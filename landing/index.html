Self-hosted issue tracker

The issue says Done. The pull request is still open.

team-hub is a self-hosted issue tracker for software teams: the core of Jira, tied to the code and to the knowledge base instead of bolted onto them. Where an issue’s status and its code disagree, it says so.

For developers and team leads who would rather run their own tracker than rent one.

The tracker itself

Projects, issue types, epics and subtasks, configurable workflows, scrum and kanban boards with drag and drop, a backlog with sprint planning, releases with release notes, comments with mentions, attachments, links, time tracking, watchers and notifications, a query language, saved filters, bulk changes, an activity feed, and live updates in every open browser.

01Code

Status and code cannot silently disagree.

Connect a GitHub repository and the tracker reads what happens there. An issue key in a branch name, a commit message or a pull request title is enough to tie them together.

Drift

Drift is where an issue’s status and its code tell different stories. In review, but changes were requested. Still to do, though the code exists. Checks are failing. In progress for days with no branch or commit.

The same triangle shows on the board, in the backlog and in search, and drift is not empty is a query like any other.

The code is on the issue

Branches, commits and pull requests appear on the issue they mention, with the state of the review and of the checks. The command that creates the issue’s branch is one click to copy.

The code moves the issue

A branch starts the issue, a pull request puts it in review, the last merge finishes it. Each rule is set per project and can be “do nothing”. Finished work is not reopened, and a merge finishes an issue only when none of its pull requests is still open.

Commit messages can comment, log time and move issues:

WEB-12 #comment fixed the redirect #time 1h 30m #in-review

02Knowledge and tests

What the team wrote down and what the tests say, on the same issue.

A knowledge base linked both ways

Spaces of Markdown pages in a tree, with history, diff and full-text search. A page that mentions WEB-10 shows up on that issue by itself, and the issue lists its pages.

A task list on a page can become issues. Confluence spaces can be imported as a mirror that is kept up to date.

Tests that know which issue they verify

Runs of the e2e testing framework arrive through a reporter. A test that carries an issue key in its title or tags is linked to that issue, so the issue shows whether what it describes actually works.

A failing test on an issue that is marked Done is shown for what it is.

03AI agents

An agent proposes, a person decides.

Work on an issue can be handed to an agent from the issue’s page: refine the description, break it into subtasks, review the pull request, implement it in code, or a task in your own words.

A run shows what the agent did, asks when it needs a decision, and ends in proposals: a comment, a status change, subtasks. Nothing changes until someone approves it, unless the project’s administrator chose to trust a kind of change.

Who carries a run out

The server carries out the runs that need no code, with your own model provider key. Runs that need the repository go to a runner: the desktop app, the hub command line, or anything that speaks the run contract.

Also an MCP server

A coding agent working in the repository can read its issue, comment, move it and look things up in the knowledge base, with the permissions of the person whose token it uses.

04Desktop app

Nothing leaves your computer without a click.

A developer’s cockpit for macOS, Windows and Linux. The issues assigned to you become agent threads: an agent works on an issue in your local clone, in a git working tree and branch of its own, and whatever should leave your computer (a comment, a status change, a push, a pull request) waits for your click. The same app is a runner for work delegated on the web.

The safety model, in plain words

  • One working tree and branch per thread. Your checkout, index and branch are never touched.
  • The agent’s shell runs in the operating system’s sandbox: no network, writes only inside its working tree. Where the system has no sandbox, the thread gets no shell at all unless you allow one.
  • The agent never holds your token. It lives in the system keychain, and the offline copy of your tracker is encrypted.
  • A push shows exactly the commits and the diff, pushes exactly the commit you looked at, and is never forced.

The whole list, and what was tried against a real model

Download

Installers for macOS, Windows and Linux go to the repository’s releases page. The first release is being prepared; if the page is still empty, build the app from apps/desktop.

The builds are not signed yet, so macOS and Windows will warn before the first start. The app needs a team-hub server to connect to. For real agents it uses Claude Code signed in on the same machine, or an Anthropic API key.

05Search, reports, plans

A query language, reports and a timeline over the same data.

The query language

Plain words search the text; a bare key opens the issue. Modules add fields of their own: pr and drift come with the code module. A query can be saved as a filter, and its result exported as CSV.

Search folds accents, so zolta finds żółta. 

project = WEB AND sprint in openSprints() AND assignee = currentUser()
type = Bug AND priority >= High AND created >= -7d ORDER BY priority DESC
text ~ "kod pocztowy" AND category != done
category = done AND pr = open            -- with the github module
drift is not empty                        -- status and code disagree

Reports reconstructed from history

Burndown, velocity, cumulative flow, cycle time and workload are computed on request from the issues’ recorded history. Nothing is stored, so a report always agrees with what the history says today.

A timeline of epics

A project’s epics as bars from start date to due date, with sprints and releases behind them. Drag a bar to plan; an epic nobody has dated shows the span its issues suggest.

06Modules and import

Take what you need. Bring what you have.

Modules you can switch off

Everything beyond the tracker is a module: code, knowledge base, timeline, reports, tests, agents, the importers. A module can be switched off for the whole instance or for one project. Its data stays; it shows nothing and receives nothing until it is switched on again.

Or leave it out of the build and name the ones to keep:

$ cargo build --release -p hub-server \
    --no-default-features --features github,wiki

New ones plug in the same way: writing a module

Import from Jira and Confluence

Jira Cloud and Server/Data Center over their API, or a CSV export, with the issue keys kept, history, comments, worklogs, sprints, versions and links. Statuses, types and people are mapped in a preview before anything is written, and an imported project can be brought up to date again later.

Confluence spaces come into the knowledge base as a mirror.

Both imports have been tested against local fakes only, not yet against a real Jira or Confluence.

07How it is built

One binary, one data directory.

Server
Rust. One binary, team-hub: the HTTP API, the live stream, and it serves the built interface.
Data
SQLite in one file under the data directory, with FTS5 for text search. Attachments and the instance key sit next to it; that directory is what you back up.
Beside it
Nothing to run. No database server, no queue, no cache. GitHub, Jira, Confluence and a model provider are things you connect if you use them.
Interface
React and TypeScript, built with Vite. English and Polish, light and dark.
Modules
One folder each: a Rust crate and its screens, behind a Cargo feature. A module left out of the build has no tables, no routes and no entry in Settings.
Sign-in
Passwords hashed with Argon2, sign-in attempts rate limited. API tokens are stored hashed and shown once. Tokens of other systems are encrypted at rest with the instance key and never returned by any route.
Desktop app
A Tauri window over a Rust core that is also the hub command line. An agent’s turn runs through the Claude Agent SDK.

08Run it

Three commands, or one container.

Building from source needs Rust (stable) and Node 22; the container needs only Docker.

Open http://localhost:8080. The first visit creates the administrator account, optionally with example projects, a team and a few weeks of history to look around in.

The server binds to 127.0.0.1 by default; put a TLS-terminating proxy in front before exposing it. Wherever the address is reachable by others before you have set the instance up, set TEAM_HUB_SETUP_TOKEN: creating the first account then asks for it.

On Railway the repository deploys as it is: a volume at /data, a public domain and two variables.

README: Running it README: In a container

From source, in a clone of the repository

$ cargo build --release
$ (cd web && npm install && npm run build)
$ ./target/release/team-hub

In a container

$ docker build -t team-hub .
$ docker run -p 8080:8080 -v team-hub-data:/data \
    -e TEAM_HUB_SETUP_TOKEN=choose-one team-hub

The image holds the server and the built interface, listens on all interfaces, and keeps everything in /data. Back up that directory.

09Not yet

What it does not do yet.

This list is the README’s, not a roadmap with dates. It is here so that you find out now rather than after you have set it up.

Missing, each meant to arrive as a module

  • E-mail notifications
  • Custom fields
  • Automation rules beyond the code-driven ones
  • GitLab as a second code host (the drift rules and badges are host-neutral already)
  • Single sign-on

Known gaps in what is there

  • Tested only against local fakes, never against the real thing: the Jira and Confluence imports, the GitHub API calls, and the server’s own agent runs (a fake model).
  • The desktop app has run on Linux only. Its macOS and Windows sandboxes, the tray, notifications and installers are unverified.
  • The server writes English. The interface puts its errors, notifications and status lines into Polish as they arrive; the descriptions of agent tools, which the agent itself reads, stay English.
